# 관할별 서식 수집 · 규칙 학습 전략 v0.1

2026-09-13 | 전제: 형제 조항은 관할마다 있기도 없기도 하다. 규칙은 서식에서만 나온다.

## 0. 결론

**서식은 이미 공개돼 있다. API를 기다릴 필요가 없다.** 조사 중 확인한 세 가지가 수집 난이도를 크게 낮춘다.

1. 교육지원청이 배치계획과 서식을 **홈페이지 공지·자료실에 공개 게시**한다.
2. 첨부에 **XLSX로 된 특수학급 설치교 현황**이 붙는 사례를 확인했다. HWP 표 파싱 없이 바로 읽힌다.
3. 같은 시도 산하 지원청은 **동일 CMS를 쓴다.** 관할 수만큼 크롤러를 짤 필요가 없다.

실제 확인 사례 — 경기도성남교육지원청 특수교육지원센터 자료실에 게시된 **「2025학년도 수원 유·초·중학교 입학 특수교육대상자 선정·배치 일정 안내」**. 첨부 3건 중 HWP 2건(제출서류 양식, 적응행동검사 안내)과 **XLSX 1건(2024년 특수학급 설치교 및 특수학교 현황)**. 앞뒤 글은 의정부·김포 안내다.

여기서 두 가지가 더 읽힌다. **지원청이 서로의 안내를 교차 게시**하므로 한 게시판에서 여러 관할 자료가 나온다. 그리고 우리가 [데이터소스 API 확보검증](데이터소스_API_확보검증.md)에서 “문서에서 꺼내야 한다”고 했던 L2 설치교 목록이 **이미 구조화된 파일로 배포되고 있다.**

## 1. 규모

전국 교육지원청은 **176개**다(17개 시도교육청 산하, 2024년 교육부 제도개선 계획 기준).

중입 배치계획은 교육지원청 단위로 발간되므로 이론적 상한이 176개다. 다만 실제 목표는 단계적이다.

| 단계 | 범위 | 근거 |
|---|---|---|
| MVP | **1개 관할** (강동송파) | 이미 원문 확보, 교사 검수 가능 |
| 시범 | 서울 전체 | 동일 CMS(`*.sen.go.kr`), 시교육청이 통합 계획도 공표 |
| 확장 | 경기 | 동일 CMS(`goe**.kr`), 확보한 수원 사례 활용 |
| 전국 | 176개 | 시도별 어댑터 17개 수준으로 커버 |

크롤러 단위는 **관할이 아니라 시도**다. 176개가 아니라 17개 어댑터 문제로 바뀐다.

## 2. 수집 파이프라인

```
시도별 게시판 어댑터 → 게시물 수집 → 첨부 원본 보관 → 파싱 → 규칙 추출(LLM)
  → 원문 인용 병기 → 교사 검수 → rule_version 확정 → 서비스 반영
```

| 단계 | 내용 | 주의 |
|---|---|---|
| 수집 | 시도별 게시판 URL 패턴으로 목록 순회. 제목 키워드: `특수교육대상자`, `선정`, `배치`, `입학` | robots.txt와 이용약관 확인. 과도한 요청 금지 |
| 보관 | 첨부 원본 + **출처 URL · 게시일 · 파일 해시** | 원본을 버리면 검증이 불가능해진다 |
| 파싱 | HWP는 hwp5/hwpx 추출, XLSX는 직접 | 표 구조 손실 시 원문 텍스트도 함께 보관 |
| 추출 | LLM으로 규칙 스키마(§3)에 매핑 | **추출값만 저장하지 않는다.** 근거 문장을 함께 저장 |
| 검수 | 교사가 규칙 행별로 확인 | 검수 전 규칙은 서비스에 반영하지 않는다 |

**AI 사용 범위가 넓어진다.** 02 기획서 §3-1은 AI를 B 트랙(수기서류 OCR)에만 쓴다고 썼으나, 이제 **A 트랙의 서식→규칙 추출에도 들어간다.** 기획서를 수정해야 한다. 다만 두 경우 모두 원칙은 같다 — 추출은 초안이고, 확정은 사람이 한다.

## 3. 규칙 스키마

서식에서 뽑을 항목을 고정해야 수집이 반복 가능해진다. 03 문서 §3 규칙 테이블을 확장한다.

| 규칙 키 | 값 | 비고 |
|---|---|---|
| `district_office` `admission_year` `application_type` | 식별자 | 규칙 행의 기본 키 |
| `reference_map` | 카카오맵 / 포털지도 / 학구도 | 관할별로 다름 |
| `nearby_row_count` | 정수 | D·S=3, G=4 |
| `guardian_preference_row` | required / optional / none | 동부 필수 여부 미확인 |
| `duplicate_check_scope` | 근거리 행끼리 / 전체 | 보호자 희망 중복은 허용 |
| `class_type_consistency` | 통일 필수 / 혼재 허용 | |
| `walk_transit_boundary_m` | 정수 | D·S=2000 |
| `boundary_inclusive` | 미만 / 이하 | **G의 ‘정확히 2km’ 중복 문구 unresolved** |
| `departure_point` | 거주지 / 아파트 동 포함 / 등본 도로명 | |
| `display_under_1000m` | m 일의 자리 / 미확인 | S만 확정 |
| **`sibling_rule_exists`** | **true / false / unknown** | **§4** |
| `sibling_rule_text` | 원문 인용 | exists=true일 때 필수 |
| `sibling_form_id` | 서식 번호 | G=서식8~11 |
| `special_school_branch` | 1순위 특수학교 / 해당없음 | |
| `source_document` `source_locator` `verified_at` `reviewed_by` | 출처·검수 | 모든 행에 필수 |

## 4. 형제 조항 — 3-state를 유지한다

관할마다 있기도 없기도 하다는 것이 핵심이다. 따라서 **`unknown`을 `false`로 접지 않는다.**

| 상태 | 의미 | 화면 동작 |
|---|---|---|
| `true` | 해당 관할 서식에 형제 조항 확인 | 특이배치 서식·증빙 안내, 보호자 희망 행에 형제 학교 제안 |
| `false` | 원문을 읽었고 조항이 **없음을 확인** | 형제 입력 자체를 숨기거나 “해당 관할 서식에 없음” 표시 |
| `unknown` | 아직 원문 미확보 또는 판단 보류 | **“관할 규칙 확인 중”** 배지. 자동 안내 금지 |

현재 상태: G(강남서초)=`true`(서식8~11 확인), D·S=`unknown`(원문 재확인 필요), 그 외=`unknown`.

세 상태를 구분하지 않으면 조항이 없는 관할에서 없는 규칙을 안내하게 된다. 그게 이 서비스가 가장 하면 안 되는 실수다.

## 5. “교육청에 API 요청” 경로

요청 자체는 법적 근거가 있는 실재하는 제도다.

- **공공데이터법 제27조** — 공표된 제공목록에 없는 공공데이터는 해당 기관 또는 지원센터에 **제공신청**할 수 있다.
- **제31~32조** — 제공 거부·중단 통지를 받으면 **60일 이내 분쟁조정** 신청이 가능하다.

다만 우선순위는 낮다. **서식은 이미 공개돼 있어 청구할 필요가 없다.** 청구가 의미 있는 대상은 따로 있다.

| 청구 대상 | 가치 |
|---|---|
| 배치계획 HWP | 낮음 — 이미 공개 게시 |
| **기계판독 가능한 설치교 목록**(XLSX/CSV 전 관할) | 중간 — 일부는 이미 XLSX로 배포 중 |
| 규칙의 구조화 제공 | 낮음 — 기관이 이런 형태로 보유하지 않는다 |

**진짜 목표는 API가 아니라 검수 관계다.** 교육지원청이 우리 규칙 테이블을 확인하고 “이 관할 규칙이 맞다”고 인정해주는 쪽이, 원본을 받아 우리가 해석하는 것보다 정확하고 책임 소재도 분명하다. 02 기획서의 기관용 서비스 가설과도 이어진다.

## 6. 지속가능성 — 매년 갱신

이 전략의 진짜 비용은 수집이 아니라 **갱신**이다. 계획과 서식은 매 학년도 새로 나온다.

- 게시판 신규 글 감지 → 변경 후보 알림 → 교사·담당자 재검수 → `rule_version` 증가
- 전년 규칙은 삭제하지 않고 버전으로 보관한다. 과거 신청 건의 근거가 남아야 한다
- 02 기획서 §3-1이 지적한 “매년 바뀌는 정보의 갱신 책임과 비용 확보”가 여기에 해당한다. 사업화 논의에서 이 운영비를 명시해야 한다

## 7. 왜 이게 해자인가

지도는 누구나 만든다. 수원 레퍼런스가 증명했다. 복제하기 어려운 건 **검수된 관할별 규칙 테이블**이다.

- 원문이 HWP로 흩어져 있어 수집 자체에 시간이 든다
- 규칙 해석에 현장 교사의 확인이 필요하다
- 매년 갱신해야 해서 한 번 만들고 끝나지 않는다
- 관할이 늘수록 후발 주자의 추격 비용이 선형으로 증가한다

## 8. 다음 작업

1. 서울(`*.sen.go.kr`)과 경기(`goe**.kr`) 게시판의 **URL 패턴·게시판 ID를 실제로 확인**하고 어댑터 1개를 시범 작성한다.
2. 확보한 D·S·G 3종을 §3 스키마에 채워 **규칙 테이블 v1**을 만든다. 빈 칸은 `unknown`으로 남긴다.
3. **강동송파·동부 원문에서 형제·특이배치 조항을 재확인**해 `sibling_rule_exists`를 확정한다.
4. 성남 자료실의 XLSX 설치교 현황을 받아 **L2 스키마 적합성**을 검증한다. 다른 관할도 같은 형식인지 확인한다.
5. 게시판 이용약관·robots.txt를 확인하고 수집 방식의 적법성을 정리한다.

## 9. 기존 저장소 문서와의 관계 · 정정

[고입·지역공개자료 확보검증](../research/고입_및_지역공개자료_확보검증.md) E7이 이미 서울·경기(용인·수원)·인천·제주·경남 표본을 조사했고, **경기 용인과 인천의 XLSX 학교(급) 현황 공개를 먼저 확인했다.** §0의 XLSX 발견은 새로운 사실이 아니라 성남 사례가 추가된 것이다.

이 문서가 E7에 더하는 것은 두 가지다.

**① 지원청 간 교차 게시** — 성남 자료실에 수원 안내가, 앞뒤 글에 의정부·김포가 있다. 한 게시판에서 여러 관할 자료가 나온다. E7의 “같은 지역의 본청과 지원청 중복 게시를 추적한다”를 지원청 간으로 확장한다.

**② CMS 계열** — 수집 단위를 관할이 아니라 CMS로 잡을 수 있다. E7이 수집한 URL로 확인되는 계열은 최소 3개다.

| 계열 | URL 패턴 | 확인된 기관 |
|---|---|---|
| A | `/na/ntt/selectNttInfo.do?bbsId=&mi=&nttSn=` | 경기 용인 `goeyi.kr`, 수원 `goesw.kr`, 성남 `goesn.kr`, **인천 `ice.go.kr`** |
| B | `BD_selectBbs.do` · `/CMS/notice/...` | 서울 본청 `sen.go.kr`, 북부 `bbedu.sen.go.kr` |
| C | `/board/view.jje` | 제주 `jje.go.kr` |

계열 A가 **시도 경계를 넘어 경기와 인천에 걸쳐 있다.** §1에서 “시도별 어댑터 17개”라고 썼으나, 실제 단위는 시도가 아니라 CMS 벤더이므로 **어댑터 수는 그보다 적을 가능성이 높다.** 다만 표본 3개 계열만 확인했으므로 전국 커버리지를 단정하지 않는다.

### 정정 사항

- §1 “시도별 CMS 통일 → 어댑터 17개 수준” → **“CMS 계열 단위, 확인된 계열 3개, 전체 계열 수는 미확인”** 으로 읽는다.
- §0의 XLSX는 E7이 먼저 확인한 사항이다. 이 문서의 기여로 표기하지 않는다.
- 자동 수집의 적법성은 여전히 미검증이다. E7의 “원문 재배포·자동 수집 이용조건도 실제 운영 전에 확인한다”를 그대로 승계한다.

### 규칙 스키마 추가

[MVP 범위정의](MVP_범위정의.md) §9에 따라 §3 스키마에 `capacity_considered`(true/false/unknown)와 `capacity_rule_text`를 추가한다. 형제 조항과 같은 3-state 원칙이다.
